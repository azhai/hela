# M27：内存层次实测 —— 布局决策所依据的那条曲线

> 一句话：`#align(64)` / `#share` / 「writer-bearing 类型必须是整 cache line」都是在赌一条曲线；
> 这条曲线以前是**引用**（"x86 是 64"），现在是在本机**测出来**的。

## 1. 为什么这一块必须自己测

Hela 的主张是「字节在哪」。但「在 L1 还是 DRAM」决定了同一份代码是 1.4 ns 还是 100 ns，
而这个差别**不写在任何头文件里**：

- cache line 多大：Linux x86-64 是 64，Apple Silicon 是 **128**，多数 ARM64 服务器又是 64。
  这不是"架构常量"，是具体机器的实现细节。
- 各级容量：`sysctl` 只报 L1/L2（`hw.l1dcachesize` / `hw.l2cachesize`），不报 L3/SLC，
  而且在 M 系列上 `hw.l2cachesize` 报的是**簇内共享**的那块（4 MiB），不是每核独占。
- 带宽与延迟：完全测出来才有，而且随核数、频率档位、内存通道变化。

所以 `tests/hela/membw` 不是"性能彩蛋"，它是本项目所有布局规则的事实基础：
M25 的「元素必须是整条 cache line」如果按 64 算，在本机只覆盖了**半条线**。

## 2. 本机事实（`sysctl`）

| 项 | 值 |
|---|---|
| CPU | Apple M4，10 核（4 P + 6 E，`hw.ncpu=10`） |
| **cache line** | **128 B**（`hw.cachelinesize`） |
| L1I / L1D | 128 KiB / 64 KiB（`hw.l1icachesize` / `hw.l1dcachesize`） |
| L2 | 4 MiB（`hw.l2cachesize`，P 簇共享） |
| L3 / SLC | 无 sysctl 暴露（`hw.l3cachesize` 不存在） |
| 内存 | 16 GiB，页 **16 KiB**（`hw.pagesize`） |
| 频率 | **不暴露**（`hw.cpufrequency` 报 24 MHz，是定时器）→ 本文全部用 ns，不用臆测的 cycles |

最后一行是个正经结论：**Apple Silicon 不给你时钟**，所以任何"这个操作 N 个周期"的说法在这里
都得加一个假设。用 ns + GB/s 是唯一诚实的口径。

## 3. 实测：延迟（依赖加载，随机环，每元素 128 B）

指针追逐（每个元素存下一个元素的下标，128 B 间隔保证一行只放一个），全随机顺序 →
预取器和乱序窗口都插不上手，测到的就是数据**所在那一级**的延迟：

| 大小 | ns/次访问 | 判读 |
|---|---|---|
| 16–128 KiB | **1.38–1.41** | L1D 命中（64 KiB 之内） |
| 256 KiB – 2 MiB | **5.42–5.73** | L2 命中（4 MiB 之内） |
| 4 MiB | 6.97 | L2 边缘 |
| 8 MiB | 11.12 | 出 L2（大概率经 SLC） |
| 16 MiB | **70.41** | DRAM |
| 64 MiB | 95.14 | DRAM |
| 256 MiB | 99.58 | DRAM |

台阶非常干净：**1.4 / 5.5 / 100 ns**，比 L1→L2 是 4 倍、L2→DRAM 是 18 倍。
按 4.4 GHz P 核标称频率折算约 6 / 24 / 440 个周期——但见上一节，这个折算只是量级参考。

## 4. 实测：带宽

### 4.1 单线程流式读（4 个累加器）

| 大小 | GB/s |
|---|---|
| 8 KiB | 92.98 |
| 32 KiB | 91.65 |
| 128 KiB | 93.27 |
| 512 KiB | 87.01 |
| 2 MiB | 85.78 |
| 8 MiB | 88.77 |
| 32 MiB | 74.08 |
| 128 MiB | 64.44 |
| 512 MiB | 62.94 |

注意 L1 的 93 GB/s 和 L2 的 86 GB/s 几乎一样：**单核的瓶颈不是 cache，是每周期能发射的
load 数**（128 位 load × 4 路 ≈ 每周期 64 B）。所以"L1 比 L2 快多少倍"在带宽上不成立。

### 4.2 复制（读+写一起算）

| 大小 | GB/s |
|---|---|
| 8 KiB | 192.85 |
| 32 KiB | 159.34 |
| 128 KiB | 146.45 |
| 512 KiB | 145.83 |
| 2 MiB | 145.56 |
| 8 MiB | 123.60 |
| 32 MiB | 87.41 |
| 128 MiB | 84.10 |
| 512 MiB | 83.60 |

`memcpy` 在 DRAM 上 84 GB/s（读+写合计），单线程读是 63 GB/s——**复制不是"两份流量"那么贵**，
因为写走的是另一条路径（store buffer / 写合并）。

### 4.3 多线程聚合读（512 MiB 分片）

| 线程 | GB/s |
|---|---|
| 1 | 61.25 |
| 2 | 69.63 |
| 4 | 75.37 |
| 6 | 95.75 |
| 8 | 100.09 |
| 10 | 101.43 |

**内存天花板 ≈ 100 GB/s**（10 线程），单线程只吃到 61%。

4 → 6 线程那一跳（75 → 96）不是噪声：4 个 P 核共享一个 L2 与一套端口，第 5、6 个线程落到
E 核簇上，是**另一套** L2/端口，于是聚合带宽又涨了一截。这条曲线说明"按核数线性扩展"
的假设在 4 核之后就不成立了。

## 5. 实测：扫描宽度（这条直接改了 xrep）

256 MiB 全 `0xFF`，找一个不存在的字节（最坏情况：必须扫完），每个实现取 5 次最快：

| 实现 | GB/s |
|---|---|
| `bytes.index_byte`（单候选，1 趟） | 62.4–64.6 |
| `index_byte` ×2（双候选，**2 趟**） | 30.3–32.2 |
| 手写 `u8x16` ×4 单趟双候选 | 62.5–65.0 |

结论有两条，都很硬：

1. **SIMD 早就用上了**。`core:bytes.index_byte` 在 arm64 上每轮扫 64 字节（4 个 128 位向量），
   已经贴着 DRAM 带宽跑（62 GB/s vs 天花板 63 GB/s 单线程）。在这上面再"上 SIMD"没有空间。
2. **空间在趟数上，不在宽度上**。大小写不敏感搜索要两个候选字节，`min(index_byte(a),
   index_byte(b))` 是两趟完整扫描 → 30 GB/s，正好是一半。单趟双候选拿到 63 GB/s，
   也就是**把流量砍一半**，而不需要更宽的向量。

这条结论已经回流到 xrep（`search/scan.odin` 的 `index_either`），并且顺手修掉了一个
二次复杂度的病：命中密集 + 大小写不敏感时，旧写法里"第二个候选"每次都要扫到文件末尾，
64 MiB / 840 万命中实测 **34.6 s → 41 ms**。

## 6. 实测：read(2) / mmap / 设备本身

1 GiB 文件，写入时就用 `F_NOCACHE`（否则你测的是 DRAM，见 7.2）：

| 方式 | GB/s | 说明 |
|---|---|---|
| `read` + `F_NOCACHE`，1 个读者 | **1.81** | 队列深度 1：同步读，驱动器大部分时间在等下一个请求 |
| 同上，2 个读者 | **3.15** | |
| 同上，4 个读者 | 3.09 | 盘已饱和 |
| 同上，8 个读者 | 3.10 | |
| `read_entire_file` + 求和（热） | 9.62–9.89 | 页缓存命中，但要 memcpy 进堆 |
| `mmap` + 求和（每次重新映射，含缺页） | 12.89–13.25 | 不复制，但要为 65536 个 16 KiB 页各付一次缺页 |

三件事：

- **这块 SSD 的顺序读上限 ≈ 3.1 GB/s**，而单线程同步读只拿到 **1.8 GB/s**（58%）。
  "接近固态硬盘极限"这句话，如果单线程测出来超过 3.1 GB/s，那测的一定不是盘。
- 热缓存下 mmap 比 `read_entire_file` 快 **~30%**，省掉的正是那次 memcpy；
  但它并不"免费"——缺页 65536 次，摊在 78 ms 里。
- **冷数据下两者都被盘按住（1.8–3.1 GB/s）**，mmap 一点忙都帮不上。所以对"扫一遍语料库"
  这种场景，真正的杠杆是**并发读**（队列深度），不是零拷贝。

## 7. 三个真坑（都是"测出来像结论"的那种）

### 7.1 依赖加载环会被优化器整段删掉

第一版 latency 探针每个尺寸都报 `0.00 ns`。原因不是测量精度，是 `cur = p[cur]` 的结果没人用
（`_ = cur` 不算），LLVM 判定整段循环无副作用，直接删了——**计时器测了一段不存在的代码**。
修法是一个包级 `sink ~= cur`。这类坑最危险的地方在于它不报错、数值还"稳定"。

### 7.2 不设 `F_NOCACHE` 就写入，"设备速度"其实是 DRAM 速度

第一版用普通 `os.create` 写 256 MiB，紧接着用 `F_NOCACHE` 读回来，测出 **14 GB/s** ——
比这块盘的物理上限高 4 倍。因为刚写完的页还脏在统一缓冲区里，`F_NOCACHE` 只影响"读时要不要
填缓存"，不影响"已经在缓存里的脏页"。必须**写入路径就带 F_NOCACHE**，数据才真的落到设备上。

顺带一个：`posix.open(path, {.WRONLY, .CREAT, .TRUNC})` 缺 mode 参数时，文件权限是**垃圾值**
（实测 `--wx------`），于是后面的只读打开直接 `EACCES`。要么传 `{.IRUSR, ...}`，要么别用
`CREAT`。

### 7.3 cache line 是 128，而编译器的默认值是 64

`get_layout_cache_line()` 在没给 `-layout-cache-line` 时返回 `LAYOUT_DEFAULT_CACHE_LINE = 64`。
在这台 M4 上：

- 清单里的 `cache_line` / `cache_lines` / `spans_cache_line` / `--waste` 全部按**半条线**算；
- M25 的「含 `#share` 的类型 size/align 必须是 cache line 整数倍」在 64 的倍数上就通过，
  但相邻两个元素仍然共用一条 128 B 线——规则在**纸面上**成立，在**机器上**不成立。

不改默认值的理由：默认值必须是**可移植**的（x86-64 与多数 ARM64 服务器是 64，
Apple Silicon 是 128，没有任何一个数能覆盖全部），而 `-layout-cache-line:128` 是显式声明。
所以这里的正确处理不是"改常量"，而是：
1. 清单里每个类型都带 `cache_line` 字段（已有），假设因此**可见**；
2. 想拿本机真值就显式传参，本文所有数字都是在 128 的口径下才有意义；
3. 断言不要写成"等于 8"这类依赖本机的值（M26 已经踩过 `linux_i386` 那次）。

这也是"AI 读清单而不是猜 padding"的又一层：**清单里的 `cache_line` 是假设，不是事实**，
它来自构建参数。下一轮该做的是让 `hela-layout --waste` 在报告开头打印它用的是哪条线。

## 8. 交付

- `tests/hela/membw/main.odin`（新）：六段探针（延迟 / 读 / 复制 / 多线程 / 扫描 / IO），
  `quick` 模式把尺寸缩小并跳过 1 GiB 设备段，全程 < 1 s；完整模式约 30 s。
- `tests/hela/run.sh`：28 → **29 步**（新步骤 28），并进严格 `vet` 列表。
- 探针自带断言：扫描函数若"找到了不该存在的字节"就直接 panic，所以 run.sh 跑到最后一行
  也证明了两候选单趟扫描与 `index_byte` 的判定一致。

## 9. 取舍

- **不引第三方基准框架**：需要的是"这条曲线长什么样"，不是统计显著性。取最快一轮 +
  固定 seed，噪声只会让数字变慢，不会变快。
- **不报 cycles**：拿不到时钟就不猜。ns 与 GB/s 是这台机器上唯一无假设的口径。
- **不把设备数字放进 run.sh**：写 1 GiB 属于"机器体检"，不属于"编译器回归"。
