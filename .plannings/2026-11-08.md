## Hela M26：`layout_hash_of` + 运行时 ABI 握手（承接 11-07 的 M24/M25）

- 动机：`layout_hash` 以前只存在于构建产物（清单 JSON/CBOR）里，**程序自己不知道自己是什么形状**。
  于是残留失败模式是「构建后读到错位字段」：陈旧二进制、混装版本、共享内存/文件的上一任写者。
- 先抽真源：新增 `src/layout_hash.cpp`（`LayoutField`、`layout_fields_of_type`、`layout_kind_name`/
  `layout_soa_name`、`layout_hash_combine`、`layout_hash_of_type`），由 `checker.cpp` 在 `bit_layout.cpp`
  之后 include；`layout_writer.cpp` 改为调用。**6 份 golden（abi + 5 个 cross）一字未变 = 重构正确的证明**。
- 新 intrinsic `intrinsics.layout_hash_of($T) -> u64`：编译期常量，与清单同一个函数；
  `#assert(layout_hash_of(Wire) == 0x2873f36e4697a61d)` 成为**不需要 golden 文件的 ABI 门禁**。
- 新库 `core:hela/abi`：24 B `Stamp #explicit #align(8)`（magic/version/flags/hash/size/align）+ 手写小端
  `stamp_encode`/`stamp_decode` + `verify`（8 种原因：Bad_Magic/Bad_Version/Bad_Flags/Layout_Drift/
  Size_Mismatch/Align_Mismatch/Short_Buffer/Misaligned_Payload）+ `publish`/`share_as`（**只在 .OK 时给指针**）。
- 测试 `tests/hela/hash`：整包 **16 个类型**的清单 hash 与编译期常量逐行 diff（`--hashes | sed s/^[^:]*:://`
  对比程序打印的 `<Name>\t<hash>`）；7 条等价/差异 `#assert`（同名/换序/命名 padding/aosoa/数组形状/位段/atomic）；
  2 条 ABI pin；运行时 8 类误配 + 截断 + 文件 artifact 改一位后报 Layout_Drift。
  `run.sh` **28 步**（新步骤 27，TSAN 后移 28），`core:hela/abi` 进严格 vet 循环。
- 四个真坑（都进了 `22-m26-layout-hash.md`）：
  1. **必须对 `base_type` 取 hash**：直接对 `$T` 取，别名是 `Type_Named` → `layout_kind_name` 落 `"other"`、
     字段枚举只看 `Type_Struct` → 字段列表为空 → 所有别名**撞成同一个 hash**（`Wire` 与字段换序的
     `Wire_Reordered` 同 hash）。假一致比报错危险，靠负例 `Wire != Wire_Swapped` 守门。
  2. **`#split(N)` 会把 struct align 抬到 N**：`#explicit + _:[56]u8` 是 align 8，`#split(64)` 是 align 64
     → 同 size/offset 但 hash 不同（align 决定 `[N]T` 的 stride，是真布局）。M9「与手写 padding 字节等价」
     只在 size/offset 意义上成立。测试里留 `Padded_Loose` 当负例。
  3. 泛型过程里 `layout_hash_of(T)` 正常（Odin 只检查**特化后**的 body，未特化直接报
     `Unspecialized polymorphic procedure`）；但 `#assert(hash_of(Wire) == …)`（泛型包装）在全局作用域不行
     ——过程调用需要 context。等价性改放运行时断言。
  4. `Record`（含 u64）不钉 `#align(8)` 时 `RECORD_HASH` 在 `linux_i386` 上不成立（u64 对齐 8→4）。
     补 `#align(8)` 后同一条 pin 在 5 个 target 上通过 → 「hash 不含 target」的可操作版本：
     **一个常量在 5 个 target 编译通过 = 字节可直传**。`Padded_Loose` 的对齐断言只能写 `!= 64`
     （不能用 `== 8`），依赖「本机 u64 怎么对齐」的断言不是跨 target 断言。
- 验证：run.sh 28 步全绿（host + 5 target pin 循环）、`HELA_TSAN=1` 全绿、1072 核心测试全绿、
  `core/hela/abi` 8 个 target 交叉 check 全过。清单仍 v7，未刷新任何 golden。
- 文档：`.plannings/hela/22-m26-layout-hash.md`；00-plan 补 M26 行 + 关键文件 + 下一步改成 `#view` /
  abi 接进 io·exec / 高性能后端；README 补第 22 号文档、二十八步、手工命令、结语。

## M27：内存层次实测（hela，run.sh 29 步）

- 新增 `tests/hela/membw/main.odin`：六段探针（依赖加载延迟 / 流式读 / 复制 / 多线程聚合 /

  `run.sh` 28 → 29 步并进严格 vet，全绿（`hela layout tests: ok`）。
- 本机（Apple M4，10 核 4P+6E，16 GiB）实测：
  - cache line **128 B**（`hw.cachelinesize`）；L1I 128 KiB / L1D 64 KiB；L2 4 MiB/簇；
    **无 L3 sysctl**；页 **16 KiB**；**频率不暴露**（`hw.cpufrequency` 是定时器 24 MHz）→ 只用 ns/GB/s。
  - 延迟台阶：L1 **1.4 ns** / L2 **5.5 ns** / DRAM **100 ns**（16 MiB 起跳）。
  - 单线程流式读 L1≈93、L2≈86、DRAM≈63 GB/s；复制 84 GB/s（读+写合计）；
    10 线程聚合 **≈100 GB/s**（4→6 线程 75→96 一跳：P 簇与 E 簇各自一套 L2/端口）。
  - 扫描 256 MiB：单候选 62 / 双候选两趟 **30** / 双候选单趟 **63 GB/s** → 空间在趟数不在向量宽度。
  - 1 GiB：`read`+F_NOCACHE **1.8 GB/s（1 读者）/ 3.1 GB/s（≥2 读者，盘饱和）**；
    热 `read_entire_file` 9.6、`mmap`（含缺页）13.2 GB/s。
- 三个坑：①依赖加载环被 DCE 删掉（全报 0.00 ns → 包级 `sink ~= cur`）；
  ②不设 `F_NOCACHE` 写入则"设备速度"其实是 DRAM（测出 14 GB/s）；③`posix.open` 带 CREAT 不传
  mode 得到 `--wx------`，后续只读打开 EACCES。
- **cache line 是 128 而 `LAYOUT_DEFAULT_CACHE_LINE = 64`** → M25 的数组规则在本机只覆盖半条线；
  默认值必须可移植（x86-64/多数 ARM64 是 64），所以不改常量，改为「清单里 `cache_line` 是假设」+
  下一步让 `--waste/--contract` 打印所用线宽。
- 文档 `23-m27-membw.md`；00-plan M27 行 / README 索引 / run.sh 步数已同步；删掉根目录遗留
  602 KB 可执行 `testing`，`.gitignore` 加 `/testing`。

## xrep：ADR 0013（分支 hela）

- `engine/readahead.odin`（新）：一个读者线程 + `sync.Cond` 有界队列（深度 2），FIFO 保序 →
  「读下一个文件」与「扫当前文件」重叠而输出顺序不变。`READAHEAD_READERS=2`、
  `PARALLEL_READ_MIN=4 MiB`。实测 32×4.5 MiB 冷读 72.1→61.5 ms（1.17x）、暖 30.5→23.2 ms（1.31x）、
  **单文件 256 MiB 暖 48.1 vs 48.5（无可测差异）**。
- 三个真坑：①`Read_Item.skipped` 必须独立一位（0 字节文件 `data==nil` 被误判成"没读"）；
  ②`Chunk.file_off` 不能省 —— `os.read_at` 的 offset 是**文件绝对偏移**，第一版每段都读文件开头，
  长度对内容全错，用 32 MiB 跨段植入 `ZZZ` 才抓出来；③预读缓冲由读者线程用进程默认堆分配，
  主线程必须 `delete(data, runtime.default_context().allocator)`（4 处 bad free）。
  `readahead_destroy` 必须早于 `walk_free`（借用了 files 里的字符串）。
- **`-i` 真正的开销在块内定位**：v2（ADR 0012）用 `select` 判"块里有没有"然后**逐字节重扫**
  到命中处 —— 稀疏看不出来，1/36 密度的真实文本上每次都多走 ~18 条标量分支。
  v3 改 `select + reduce_min`（与 `core:bytes` 同手法）+ 补 16 字节块 + `l<16` 标量守卫。
  A6（16 MiB，`-o:size`，3 轮最好）：1/36 `-i` 1455→5074 MB/s（**3.49x**）、
  1/4K `-i` 29684→47761（1.61x）、1/36 word `-i` 1462→5138（3.51x）；1/1 与 sparse 敏感路径不动。
  端到端 256 MiB 暖：`-i -c z` 76.78→43.73 ms（1.76x），**与 `-c z`（42.54）回到同一条线**。
- 负面结论（都写进 ADR）：BNDM 建表双向置位 **1.01x 无收益**（保留因为语义更简单）；
  `match_rest` **不在热路径**（`-i` 开销与模式长度无关，"zzz" 79.5 vs "gamma" 80.8 ms）→
  "两候选单趟"对它没意义；单文件暖数据并行 pread 无收益。
- **测量方法本身的坑**：①折叠快路径条件写反（`lo >= 'a'` 恒假）→ 一次都没执行，而基准"没变化"
  被读成"折叠没收益"；②zsh 里 `$mode` **不做词分割**（`"-c z"` 是一个参数），一整轮基准全是假的；
  ③`--stats` 报内层 ms、python 计时是外层 wall，两者混着比才得出"差异在 profiler 之外"的错误结论。
- 测试：`search/scan_test.odin` 新增穷举（长度 0..199 × 每位置单独命中，`index_either` 与
  `index_folded` 都必须给出该位置；同长度验无命中返回 -1）。`app/bench.odin` 新增 **A6 组**
  （1/36 · 1/4K · 1/1 × 敏感/`-i`，加一个 5 字节 `gamma` 行）。用例 140→**153**（16 个文件）。
- 验收：`verify.sh` 全绿（78 golden + run2 34 + run3 56 + 单测 lib19/search40/engine33/app61）；
  与 HEAD 二进制**240 组差分对比 0 差异**（15 模式 × 16 输出模式）；`XREP_NO_READAHEAD=1` 前后

### 更正：A6 的 word 行曾跑错算法

`single_match` 按定义只看 `ctx.pattern[0]`，A6 的 "1/36 word" 行拿它跑 `"gamma"` → 实际测的是
每个 `g`。这份数据每行恰好各有一个 `g` 和一个 `z`，所以命中数与 `z` 完全相同（7,471,147），
表里看不出异常，只有 MB/s 偏低。修法：按模式长度显式选（单字节 `single_match` /
多字节 `memchr_match`）。重测后 A6（`-o:size`，3 轮最好）：

| case | algo | HEAD | now | × |
|---|---|---|---|---|
| 1/36 sens | single_match | 4729.5 | 4990.6 | 1.06 |
| 1/36 -i | single_match | 1434.5 | 4961.2 | **3.46** |
| 1/4K sens | single_match | 57554.0 | 58394.2 | 1.01 |
| 1/4K -i | single_match | 29684.6 | 47619.1 | **1.60** |
| 1/1 sens | single_match | 193.2 | 193.8 | 1.00 |
| 1/1 -i | single_match | 201.4 | 204.5 | 1.02 |
| 1/36 word | memchr_match | 4268.9 | 4429.7 | 1.04 |
| 1/36 word -i | memchr_match | 1365.3 | 4437.1 | **3.25** |

教训：**基准里"跑了个算法"和"跑对了算法"是两件事**，错误的算法能产出看起来合理的数字。
